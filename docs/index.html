Claude limit tracker

How much usage is 100% of Claude's 5-hour and weekly limit bars actually worth? This page estimates it from one account's real usage, in API-equivalent dollars and tokens, and tracks it over time so quiet limit changes show up as a step in the chart.

Possible limit changes

Detected automatically: a lasting step in the mix-adjusted per-window estimates (rank test, |z| ≥ 3.3, at least 6 windows each side for the 5-hour bar and 3 for weekly bars, and a ≥ 15% shift). Limit resets (e.g. a free reset being used) are times the reported utilization fell without the window's reset time changing.

    What is this?

    Claude's subscription plans show usage as percentage bars (a rolling 5-hour window and a weekly window, sometimes extra per-model weekly bars) but never say how much work 100% is. Claude Code receives the exact utilization with every response, and its logs record the exact token usage of every API call. Put the two side by side and you can work out what a full bar is worth, then watch whether that number moves.

    The numbers here are API-equivalent: what the same calls would cost at Anthropic's public API list prices. That's a common yardstick, not what a plan costs or how Anthropic meters internally.

    Method

    1. Calls. Every assistant message in the Claude Code transcripts on the tracking machine is one API call with its model and usage (input, output, cache writes split into 5-minute and 1-hour TTL, cache reads, web searches). Copies of the same call (one per content block, and again in stream logs) are de-duplicated by message id, keeping the largest counts.
    2. Utilization samples. rate_limit_event lines in Claude Code stream-json logs (or the status line sampler) give each bar's utilization (0–100%, whole percents) and its reset time. Each bar's window is identified by its reset time; it started 5 hours (or 7 days) earlier.
    3. Per window. Usage from the window start (utilization 0) to the first sample that shows the window's peak, divided by that peak, gives "100% ≈ $X" for the window. If a bar is reset early mid-window, the part after the reset is measured from its first sample instead. Windows that rose less than 20 points (5-hour) or 10 points (weekly) are skipped. The error bar is the wider of ±1 utilization point of rounding and a bootstrap (16th–84th percentile) over 10-point (5-hour) / 5-point (weekly) slices of the window.
    4. Model mix. Plans don't charge every model in proportion to API price. For each bar, a robust non-negative regression of utilization rise on per-model usage, across all window slices, gives each model's weight. "Adjust for model mix" re-expresses every window in the dominant model's dollars, so a week of a pricier-per-percent model doesn't look like a limit cut. Untick it to see the raw numbers coloured by dominant model.
    5. Current estimate (dotted line) = median of the window estimates since the last detected change (at most the last 14 days for the 5-hour bar, last 4 windows for weekly bars), with a bootstrap 95% interval for the median.
    6. Tokens. Weighted tokens are input-token equivalents using the standard API ratios regardless of model (output ×5, 5-minute cache write ×1.25, 1-hour cache write ×2, cache read ×0.1). Raw tokens just add everything up and are dominated by cache reads.

    Caveats (please read)

    • One account, one plan. Other plans have other limits. Treat the level as indicative and the changes as the signal.
    • Invisible usage biases estimates low. Anything on the account that this machine doesn't log (claude.ai in a browser, the phone app, Claude Code on other computers) raises utilization with no matching logged usage, so the bar looks smaller than it is. Robust statistics (medians, down-weighted outlier slices) limit the damage but can't remove it.
    • Unlogged helper calls. Claude Code also makes calls that never appear as transcript messages (compaction, summarising fetched pages, small helper models). Comparing its own cost totals with the logged calls suggests these add a few percent; true values are likely that much higher.
    • Timing. Utilization samples carry no timestamp of their own and are dated by the message they follow; samples only exist while Claude Code runs in stream-json mode or a status line sampler is installed. Utilization is reported in whole percents.
    • Prices are list prices checked on the date shown below; if API prices change, the dollar series changes meaning. The token views don't depend on prices.
    • Utilization above 100% does happen (the request that crosses the limit is still counted).

    Track your own account

    Everything here is produced by a small, dependency-free Python collector you can run yourself. It reads your local Claude Code logs and writes only aggregate numbers. See the repository README for setup: a status line sampler (or stream-json logs) for utilization, then python3 collector/collect.py, and an example systemd timer that refreshes a GitHub Pages copy of this site daily.
